# 项目决策记录

> 初始化日期：2026-07-28  
> 本文件记录项目级决策及其证据。候选方案不得当作已接受决策。

## 1. 使用说明

- 每项决策使用唯一的 `DEC-*` 编号。
- 已接受记录不删除、不静默改写；需要变更时追加新记录，并填写 `Supersedes`。
- 接线、需求和测试结果分别记录在 `docs/hardware-interface.md`、`docs/requirements.md` 和 `docs/test-log.md`，本文件只记录“为何决定”。
- 没有正式来源或负责人确认时，AI 结论只能作为候选。

## 2. 状态与证据模型

### 2.1 结论状态

| 状态 | 含义 | 是否可直接实施 |
|---|---|---|
| `待确认` | 资料、型号、参数或负责人决定缺失 | 否 |
| `候选` | 已有来源支持其可行性，但尚未选定 | 否 |
| `已确认` | 已由正式来源或负责人明确确定 | 需同时满足实施门槛 |

### 2.2 证据方式

| 方式 | 含义 |
|---|---|
| `无` | 尚无足够证据 |
| `资料复核` | 已核对题面、原始 PDF、datasheet 或人工审阅资料 |
| `静态核验` | 已从源码、`.syscfg` 或只读工程信息核对 |
| `实测` | 已在真实硬件上按可复现步骤取得证据 |

结论采用 `[结论状态|证据方式]` 组合，例如 `[候选|资料复核]`。静态核验不能替代硬件实测。

### 2.3 升级规则

1. `待确认 → 候选`：必须增加明确来源或约束，不能只依赖 AI 常识。
2. `候选 → 已确认`：必须有正式题面、datasheet、实际 BOM、负责人明确选择或等效证据，并引用对应决策。
3. `资料复核 → 静态核验`：必须补充可复查的源码或配置证据；不得声称已构建或运行。
4. 升级为 `实测`：必须引用 `docs/test-log.md` 中包含环境、步骤、实际结果和证据的 `TEST-*` 记录。

## 3. 来源优先级

### 3.1 比赛需求

1. 正式题面及其版本。
2. 正式评分规则、赛场通知和裁判解释。
3. 负责人明确确认。
4. AI 推导仅可形成候选或待确认项。

### 3.2 板级与模块硬件

1. 原始原理图、引脚图和模块原厂 datasheet。
2. `docs/reviewed/` 中已对照页面复核的记录。
3. `docs/hardware/` 中的项目工作记忆。
4. `docs/extracted/` 中的 OCR/提取文本，仅用于检索。
5. AI 建议。

### 3.3 当前固件

1. 可编辑源码和 `.syscfg` 是当前配置/行为依据，但本阶段只读。
2. CCS 工程元数据只用于识别工程形态。
3. 生成文件只用于核对已有名称和生成结果，绝不是编辑入口。
